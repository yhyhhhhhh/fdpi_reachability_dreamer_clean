## 结论摘要

- 当前策略熵主要作为 entropy bonus 使用，进入 actor loss 时都是减号，因此优化目标会鼓励更高熵、更大的策略标准差。
- 主策略在普通 Dreamer actor-critic 阶段使用 `Models.Agent.EntropyCoef = 3.0e-4`。
- 主策略进入 FDPI regime 后改用 `FDPIRegimeDreamer.MainFDPIRegime.EntropyCoef = 1.0e-4`，比普通阶段小 3 倍。
- dual policy 单独使用 `FDPIRegimeDreamer.DualUpdate.EntropyCoef = 1.0e-4`。
- 当前配置没有启用熵系数衰减：`EntropyCoefFinal` 由默认值等于起始值，`EntropyDecaySteps = 0`。
- `WorldModel/vae_ent` 是 RSSM 后验分布熵的日志指标，不是策略熵，也没有作为独立策略探索 bonus 使用。
- 当前没有在本地实验目录中找到已归档的 `ActorCritic/entropy`、`MainFDPI/entropy` 或 `Dual/entropy` 曲线数值，因此本笔记是代码与配置静态检查结论，不是训练曲线分析。

## 策略分布与熵的含义

主策略和 dual policy 都使用同一种 Dreamer 风格高斯分布：

```python
std = (MaxStd - MinStd) * sigmoid(raw_std + 2) + MinStd
dist = Independent(Normal(tanh(mean), std), 1)
```

当前配置中 `MinStd = 0.05`，`MaxStd = 1.0`。因此熵主要由 `std` 决定，和动作均值基本无关。对单个动作维度而言，高斯熵大约落在 `-1.58` 到 `1.42` nats 之间；`Independent(..., 1)` 会把所有动作维度的熵相加。

需要注意：这里记录的是未经过 tanh-squash 的 Normal 分布熵。代码只对均值做 `tanh(mean)`，采样动作本身来自 Normal，熵指标不等同于环境最终有效动作在动作边界内的真实离散程度。如果环境或 wrapper 后续裁剪动作，日志中的策略熵可能高估有效探索幅度。

## 普通主策略阶段

触发位置：
- `trainer.py::train_agent_step`
- 当 `MainFDPIRegime.Enable` 未启用、`step < MainFDPIRegime.StartStep`，或没有可用 `gp_critic` 时，调用 `agent.update(...)`。

当前默认训练中，`MainFDPIRegime.StartStep = 1000000`，因此 100 万 env steps 之前主策略走普通 actor-critic 更新。

普通阶段 loss 形式：

```python
policy_loss = mean(log_prob * norm_adv * weight)
entropy_loss = mean(entropy * weight)
total_loss = critic_loss - policy_loss - entropy_coef * entropy_loss
```

含义：
- `- policy_loss`：最大化 advantage 加权的 log probability。
- `- entropy_coef * entropy_loss`：最大化策略熵。
- 当前系数来自 `Models.Agent.EntropyCoef = 3.0e-4`。

潜在问题：
- `agent_base.py` 中普通阶段写法是 `entropy = dist.entropy()[:, None]`，而 `log_prob` 和 FDPI 分支使用的是 `[..., None]`。在 `dist.entropy()` 形状为 `[B, T]` 时，`[:, None]` 会得到 `[B, 1, T]`，与 `weight` 的 `[B, T, 1]` 相乘会广播成 `[B, T, T]`。这会让普通阶段熵项不是逐时间步一一对应的加权平均。
- 由于普通阶段熵系数不大，这个问题未必主导训练，但如果要认真调熵，应该优先确认或修正这个维度问题。

## FDPI 主策略阶段

触发位置：
- `trainer.py::train_agent_step`
- `MainFDPIRegime.Enable = true`
- `step >= MainFDPIRegime.StartStep`
- `gp_critic is not None`

当前配置在 100 万 env steps 后启用 FDPI 主策略更新。

FDPI 阶段 actor loss 形式：

```python
entropy_loss = weighted_mean(entropy, weight)
total = weighted_mean(loss_per, weight) - entropy_coef * entropy_loss
```

其中 `loss_per` 会按 `Gp` 风险分区：
- feasible：只保留 reward policy gradient。
- critical：保留 reward policy gradient，同时加入较弱 risk margin。
- infeasible：保留较低 reward 权重，同时加入更强 risk excess。

熵项特点：
- 熵 bonus 不区分 feasible / critical / infeasible，所有分区共享同一个 `entropy_coef`。
- 当前 `entropy_coef = 1.0e-4`，来自 `FDPIRegimeDreamer.MainFDPIRegime.EntropyCoef`。
- `_scheduled_entropy_coef(...)` 支持 `EntropyCoefFinal`、`EntropyDecayStartStep`、`EntropyDecaySteps`，但当前 YAML 没有写这些字段，`train.py` 默认让 final 等于 start 且 decay steps 为 0，所以实际是常数。
- FDPI 分支会记录 `MainFDPI/entropy`、`MainFDPI/entropy_coef`、`MainFDPI/entropy_actor_grad_norm`。

与风险项的关系：
- 熵 bonus 直接推动 actor 保持随机性。
- 风险项通过 `Gp` 对 `risk_action = dist.rsample()` 的风险评分给 actor 提供安全梯度。
- reward PG 使用的是 imagined rollout 中已经采样好的动作，`_imagined_reward_action(...)` 会 detach 该动作。

额外发现：
- `DetachActionForLogProb` 当前从配置读取并写入日志，但在 `update_fdpi_regime(...)` 中没有真正分支控制 `log_prob` 的动作是否 detach。当前 `_imagined_reward_action(...)` 总是返回 detached action。这个字段目前更像诊断标记，不是真正生效的开关。

## Dual Policy 阶段

触发位置：
- `trainer.py::joint_train_fdpi`
- `DualUpdate.Enable = true`
- `env_steps >= DualUpdate.StartStep`
- 当前配置 `DualUpdate.StartStep = 100000`

当前 dual policy 有两个更新目标，默认是 `imagined_risk_return`。

默认 `imagined_risk_return` 的 loss：

```python
dual_pg_loss = -(log_prob * risk_adv).mean()
kl_loss = KLCoeff * kl_to_main.mean()
entropy_bonus = EntropyCoef * entropy.mean()
loss = dual_pg_loss + kl_loss - entropy_bonus
```

`max_risk` 分支也是同样结构：

```python
loss = risk_loss + kl_loss - entropy_bonus
```

含义：
- dual policy 主要被训练成产生更高风险、更有信息量的动作。
- `kl_loss` 把 dual policy 拉回主策略附近，当前 `KLCoeff = 1.0`。
- `entropy_bonus` 鼓励 dual policy 不要太快塌缩，当前 `EntropyCoef = 1.0e-4`。
- 训练日志包含 `Dual/entropy`、`Dual/entropy_bonus`、`Dual/kl_to_main`，同时也写一份 `DualImag/*`。

当前判断：
- dual policy 的熵 bonus 很弱，且同时受到 `KLCoeff = 1.0` 约束。实际探索宽度大概率更多由 KL、风险优势和 std 上下界共同决定，而不是单靠 `1.0e-4` 的熵项决定。

## 当前熵配置表

| 位置 | 当前值 | 生效阶段 | 作用 |
|---|---:|---|---|
| `Models.Agent.EntropyCoef` | `3.0e-4` | FDPI 主策略启用前的普通 actor-critic 更新 | 鼓励主策略熵 |
| `FDPIRegimeDreamer.MainFDPIRegime.EntropyCoef` | `1.0e-4` | `StartStep=1000000` 之后的 FDPI 主策略更新 | 鼓励主策略熵 |
| `FDPIRegimeDreamer.MainFDPIRegime.EntropyCoefFinal` | 默认等于 `1.0e-4` | FDPI 主策略更新 | 当前无实际衰减 |
| `FDPIRegimeDreamer.MainFDPIRegime.EntropyDecaySteps` | 默认 `0` | FDPI 主策略更新 | 当前关闭衰减 |
| `FDPIRegimeDreamer.DualUpdate.EntropyCoef` | `1.0e-4` | `StartStep=100000` 之后的 dual update | 鼓励 dual policy 熵 |
| `Models.Agent.MinStd / MaxStd` | `0.05 / 1.0` | 主策略与 dual policy | 限制熵可达到的范围 |

## 目前熵的整体情况

当前实现不是无熵策略，而是三处都有熵 bonus：

1. 普通主策略阶段熵系数较大，为 `3.0e-4`。
2. FDPI 主策略阶段熵系数较小，为 `1.0e-4`。
3. dual policy 熵系数同样为 `1.0e-4`。

从机制上看，熵目前承担的是通用探索正则项，而不是安全分区自适应调节项。也就是说，代码没有在 critical 或 infeasible 区域自动降低熵，也没有在 feasible 区域额外增大熵。FDPI 的安全约束只通过 risk loss 施加，熵项始终独立存在。

这会带来一个需要实验确认的问题：如果主策略已经频繁进入高风险区，固定熵 bonus 可能仍然鼓励动作分布保持较宽；但如果过早压低熵，又可能导致策略陷入保守局部解。当前代码没有解决这个权衡，只是使用固定小系数。

## 建议后续检查

- 先检查训练日志中的 `ActorCritic/entropy`、`MainFDPI/entropy`、`MainFDPI/entropy_actor_grad_norm`、`MainFDPI/safety_to_reward_grad_ratio`、`Dual/entropy`、`Dual/entropy_bonus`、`Dual/kl_to_main`。
- 如果要做熵消融，优先比较 `MainFDPIRegime.EntropyCoef = 0 / 1.0e-4 / 3.0e-4`，并同步观察 cost rate、Gp 分区比例和任务 reward。
- 在调参前，建议先修正或确认普通阶段 `entropy = dist.entropy()[:, None]` 的广播问题，避免早期训练熵项统计和梯度含义不清。
- 如果目标是安全收敛，可以考虑让 FDPI 熵系数按分区变化，例如 feasible 保持探索、critical 降低探索、infeasible 进一步降低探索。但这属于逻辑改动，需要单独实验验证。

## 2026-06-11：4090 fast 策略学习偏弱观察

关联实验：
- [4090训练加速参数对比](../../experiments/2026-06-11_4090训练加速参数对比/实验记录.md)
- [危险区域世界模型50比50采样](../../experiments/2026-06-11_危险区域世界模型50比50采样/实验记录.md)

新的 W&B 观察：
- 原本训练在约 `1M env steps` 附近已经学会夹取。
- 4090 fast 模式接近 `4M env steps` 仍未学会夹取。
- 这说明 fast 的吞吐提升不是等价加速，至少在当前任务上过多牺牲了策略学习能力。

更新密度对比：
- baseline 每 `1024 env steps` 约有 `16` 次 agent update，`8` 次 Gp update，`8` 次 Gd update，`8` 次 dual update。
- 4090 fast 每 `1024 env steps` 只有 `2` 次 agent update，`1` 次 Gp update，`1` 次 Gd update，`1` 次 dual update。
- 即使 fast 的 batch 从 `64` 提到 `256`，optimizer step 频率也被压到 baseline 的 `1/8`，策略学习信号明显变稀。
- world model 是否同样不足尚不确定；fast 每 `1024 env steps` 只有 `2` 次 world model update，而 baseline 等效约 `16` 次，但 batch 更大。

当前判断：
- fast 更像吞吐上限测试配置，不适合作为默认长训配置。
- 当前最需要恢复的是 agent / Gp / Gd / dual 的更新密度，而不是先调熵系数。
- 熵问题仍然值得检查，但 fast 学不会夹取的首要嫌疑是策略 optimizer step 密度不足。

配置调整：
- 新增 `configs/reachability_gp_isaaclab22_4090_policy_recovery.yaml`。
- 该配置保留 `128 env + batch 256 + TF32`，但将 `TrainModelEverySteps/TrainAgentEverySteps` 调为 `512`，`AgentUpdate` 调为 `4`，`Gp/Gd/Dual UpdateSteps` 恢复为 `2`。
- 新配置每 `1024 env steps` 约有 `8` 次 agent update，介于 baseline 的 `16` 次和 fast 的 `2` 次之间，用于测试是否能恢复夹取学习速度，同时保留部分 4090 吞吐优势。
